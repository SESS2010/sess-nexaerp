# Master data import and sensitive-row retention

The master-data transfer API accepts only .xlsx workbooks generated by the matching registered master definition. The initial synchronous ceiling is 1,000 data rows per workbook. MasterDataTransfer:MaxRows may be configured lower but cannot be raised above 1,000 in this synchronous implementation.

Every import permanently retains its batch identity, master key, company and uploader identity, operational role, timestamps, file name, file size, SHA-256 hash, idempotency fingerprint, mode, final status, row counts, correlation identifier and audit/version metadata. Row number, business code, intended action, outcome, resulting record identity/version, non-sensitive error codes/messages and processing time are also permanent audit evidence.

Rejected and not-imported rows temporarily retain SubmittedValuesJson. Error objects temporarily retain AttemptedValue. RetentionExpiresAt defaults to 90 days from upload. After expiry, the purge removes SubmittedValuesJson and only the attempted-value property from each error; it keeps the error code, column, header and message. SensitiveValuesPurgedAt records completion. Successful rows never retain submitted values.

There is no scheduler. Run the guarded manual command as part of the installation operations calendar:

~~~powershell
$env:ConnectionStrings__NexaErpInstaller = '<secret installer connection string>'
$env:NexaErp__ExpectedDatabase = '<exact customer database name>'
dotnet run --project src/SESS.NexaERP.Installer/SESS.NexaERP.Installer.csproj -c Release -- master-import-retention purge
~~~

The command refuses PostgreSQL older than 17, system databases, a database other than the exact expected target, a missing advance schema, and a non-superuser installer session. It invokes the migration-owned fixed-search-path purge function in one transaction and reports the number of expired batches marked and row payloads cleared. Connection strings are never accepted on the command line.

Historical import rows and error workbooks are company-scoped. The uploader may read their own batch only while retaining the master View permission; another employee needs that master's View Audit History permission. A master definition containing commercial values must additionally declare its sensitive-result permission. For vendors this is masters.vendors / view-commercial-values; without it, GET /api/v1/master-data/imports/{batchId}/rows, the batch result, and the error workbook are denied even when the caller has audit-history access.
