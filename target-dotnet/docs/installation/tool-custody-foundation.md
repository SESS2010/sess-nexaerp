# Tool custody and opening-identity foundation

This foundation preserves individual tool custody, temporary duration in days, holder acceptance, two-party transfer, damage replacement and loss at an accepted depreciated value. Clearance reports name every outstanding individual tool across companies. These domain objects are not runtime authorization or a deployed tool register.

The opening-identity planner first reconciles each type and custody row, then expands quantities into individual ERP asset IDs with original row references. A quantity-two custody line becomes two identities, not one set. Repeat planning is deterministic; changed item/employee mappings change the review fingerprint. Actual import must enforce a single governed opening register per company and retain the fingerprint before posting. It must not turn a different workbook hash into permission to post another opening balance.

No manufacturer serials, acquisition values, depreciation, issue dates or historical acceptance are invented. The actual workbook is still required to establish the 164 types, 730 purchased, 564 issued, 166 balance, 288 custody lines and 23 holders. Synthetic fixtures establish algorithm behavior only.

Still outstanding: persisted register and custody events, real employee/role/company authorization, import posting/replay, physical-stock integration, validated Accounts/TD valuation approvals, concurrency, overdue notifications and the resignation-clearance workflow. Login revocation must remain independent of tool clearance.

Validation: isolated clean Debug/Release builds and 30/30 each. Shared frozen final candidate: clean Debug/Release builds; full Debug 999/999 and Release 996/996, zero failed/skipped; focused period, assessment, evidence, migration, installer, model and read-path checks 14/14 each. Retained TRX and all indexed source hashes verified. These results cover the final combined source; they are not fresh full-suite runs of each intermediate item commit.
